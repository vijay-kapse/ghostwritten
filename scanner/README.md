# scanner

Measures, per repo and per month since 2025-01, what share of commits on the default branch carry a public
signature of an AI coding agent. Runs nightly in GitHub Actions (`.github/workflows/scan.yml`) and commits
its output to `data/` in the format defined by `../SCHEMA.md`.

Python 3.11+, one dependency (`requests`). No cloning: everything comes from the GitHub REST API.

## Method

1. **Which commits.** Every commit reachable from the default branch whose committer date is on or after
   2025-01-01 (`GET /repos/{o}/{r}/commits?sha=<head>&since=2025-01-01T00:00:00Z&per_page=100`). Months
   are bucketed by committer date in UTC, the date GitHub's `since`/`until` filter on.
2. **Classify each commit**, in this order, into exactly one category:
   - `merge`: 2 or more parents. Excluded from the denominator, counted in `merges`.
   - `automation`: the author is a dependency, release, CI or translation bot (`AUTOMATION` in
     `signatures.py`), or any other login ending in `[bot]` that is not on the AI agent allowlist. Excluded
     from both numerator and denominator, counted in `automation`.
   - `ai`: at least one attribution rule (below) matches. Counted in `ai` and in `total`.
   - `human`: everything else. Counted in `total`.
3. **Share** = `ai / total`, where `total` is the denominator (all non-merge, non-automation commits).
   `total + automation + merges` is the raw number of commits in the month; it matches the GitHub commit
   search count for the same committer-date range (checked on vscode, pandas and cli/cli).

### Attribution rules

All matching is case-insensitive. A word in prose never counts: only `Co-authored-by:` trailers, footers that
the tools write, git identities and exact bot logins. A commit can match several rules; `by_rule` counts
each, so the rule counts of a month can add up to more than its `ai`.

| id | fires when |
|---|---|
| `claude_trailer` | a `Co-authored-by:` value contains `@anthropic.com`, `claude[bot]` or `Claude Code` |
| `claude_generated` | the message contains `Generated with [Claude Code]` or `Generated by [Claude Code]` (line breaks allowed between the words) |
| `copilot_trailer` | a `Co-authored-by:` value contains `copilot`; or a `Copilot-Session:` trailer; or the footer `Authored with GitHub Copilot` |
| `copilot_author` | author or committer login is `copilot-swe-agent[bot]`, `Copilot`, `github-copilot[bot]` or `copilot-pull-request-reviewer[bot]` |
| `codex_trailer` | a `Co-authored-by:` value contains the word `codex`, `noreply@openai.com` or `chatgpt-codex-connector` |
| `cursor` | a `Co-authored-by:` value contains `cursoragent`, `Cursor Agent`, `@cursor.com` or `cursor[bot]`; git identity `Cursor Agent`; login `cursor[bot]` |
| `devin` | login `devin-ai-integration[bot]`; or a trailer containing `devin-ai-integration` or `Devin AI` |
| `gemini` | login `gemini-code-assist[bot]` or `google-labs-jules[bot]`; or a trailer containing `gemini-code-assist`, `google-labs-jules` or `gemini-cli` |
| `aider` | subject starts with `aider: `; a trailer containing `aider`; or a git author/committer name ending in `(aider)` |
| `openhands` | a trailer containing `openhands` or `all-hands`; a git name starting with `openhands`; login `openhands-agent[bot]` |
| `amp_factory` | a trailer containing `amp-ai`, `sourcegraph amp`, `@ampcode.com` or `factory-droid`; login `factory-droid[bot]` |
| `other_bot_agent` | author or committer login is on the explicit `AGENT_BOTS` allowlist and no rule above claims it: `claude[bot]`, `chatgpt-codex-connector[bot]`, `codegen-sh[bot]`, `sweep-ai[bot]`, `coderabbitai[bot]`, `amazon-q-developer[bot]`, `tembo-io[bot]` |

Deliberately **not** counted, because people have these names or the signal is weak:
a co-author merely named Claude, Devin or Jules; any `@openai.com` address (OpenAI employees commit too);
the word `cursor`, `copilot` or `claude` in prose; `(Commit message generated by Copilot)`, which only says
who wrote the message.

The rules live as data in `signatures.py`; `signatures.json` is the same thing exported for the web
(`python signatures.py` regenerates it; a test fails if it is stale). The regexes use the subset shared by
Python and JavaScript, flags `im`.

### Scanning budget and increments

- A run reads at most **30 pages (3,000 commits) per repo**. If 2025-01 is not reached, the file says
  `complete: false` and `window_start` is the date of the oldest commit read; only months after
  `window_start` are whole.
- Later runs pick up where the last one stopped:
  - **forward:** `GET /compare/{last head}...{current head}` returns exactly the commits that became reachable
    since the last scan, including commits of merged branches dated before it. They are added to their
    months. If the last head is gone (force push), not an ancestor, or the gap needs more than the budget,
    the repo is rescanned from scratch.
  - **backfill:** while `complete` is false, the rest of the budget lists older commits
    (`until` = oldest commit read minus one second). microsoft/vscode needs 14 such runs to reach 2025-01.
  - unchanged heads cost nothing: the head lookup is a conditional request (ETag cached in
    `scanner/.cache/`, persisted between Actions runs with `actions/cache`), and a 304 does not count
    against the rate limit.
- Bookkeeping for this (last head SHA, exact oldest timestamp) is in `data/state/`; the web does not read it.

### Universe and nightly order

`universe.py` writes `data/universe.json`: the top 5,000 non-fork repos by stars from the search API
(`stars:>1000`, sorted by stars; search returns at most 1,000 results per query, so the star range is narrowed
after each 1,000), refreshed weekly, plus every `owner/repo` or `user:login` line in `data/requests.log`
(a `user:login` adds that user's 10 most recently pushed public non-fork repos).

`run.py` checks `GET /rate_limit`, keeps 25 requests in reserve, and scans in this order until the
requests or the 50-minute time budget run out: (a) requested repos never scanned, (b) top-star repos never
scanned, most stars first, (c) everything else by oldest `scanned_at`. It then writes the aggregates and prints
one line. With the built-in Actions token (1,000 requests/hour) that is about 30 first scans a night; with
a personal token in the `GH_SCAN_TOKEN` secret (5,000/hour), about 150.

### Aggregates

`aggregate.py` writes `data/leaderboards.json` and `data/summary.json`.

- Window: the last 3 full calendar months (on 2026-11-01: 2026-08..2026-10).
- A repo counts for a month only if its scan covers the whole month (`complete`, or `window_start` on or
  before the 1st). Nothing is extrapolated.
- repos / orgs (org = owner) / languages: pooled `sum(ai) / sum(total)` over the window, ranked only with
  at least 100 commits in the denominator, sorted by `ai_share`.
- tools: `by_rule` summed over the window.
- trend: one row per month since 2025-01, pooled over the repos that cover that month; `repos` says how many,
  because the set grows as scans backfill.
- summary: pooled share, median repo share and share of ranked repos with any AI commit, and the change
  from the second-to-last to the last window month over repos that cover both.

`validate.py` checks every file in `data/` against SCHEMA.md (types, formats, `ai <= total`, known rule
ids, `ai_share == ai/total`, the 100-commit ranking minimum, sort order). The workflow runs it before committing.

## Limitations

- **Signed-only, so the numbers are a floor.** Agent use that leaves no trailer, footer or bot login is
  invisible. Many tools sign by default but the signature can be turned off or edited out. Agents acting
  through ordinary user accounts are not counted: in oven-sh/bun, 1,828 of 2,349 commits in 2026-07..09
  (78%) are authored by `robobun`, a regular user account with no signature in its commits, so bun measures
  0.2% here.
- **Squash merges** collapse a pull request into one commit, which counts once. A PR's trailers survive
  only if the squash message keeps them (GitHub's default squash message keeps `Co-authored-by` lines).
  Repos using merge commits instead expose each branch commit; the merge commit itself is excluded.
- **Default branch only.** Other branches, and code that never lands, are not seen.
- **Public repos only.** Private repos are invisible to the API without access.
- **3,000 commits per repo per run.** Big repos (`complete: false`) only have whole recent months until
  backfill reaches 2025-01 over later runs.
- **Committer date**, not author date, decides the month. Rebases and squashes set it to the landing time.
- **Automation is a list.** Bots not on the list but ending in `[bot]` are treated as automation; bots
  without `[bot]` in their login and not on the list count as humans.
- **Rewritten history** (force pushes on the default branch) triggers a full rescan, which starts over
  from the newest commits.
- The universe is top-by-stars plus lookups; it is not a sample of all of GitHub.

## Reproduce one repo's number

From the repo root, with any GitHub token (scratch directory so `data/` is untouched):

```sh
cd scanner && uv venv -p python3.11 .venv && uv pip install -p .venv/bin/python requests && cd ..
GITHUB_TOKEN=$(gh auth token) scanner/.venv/bin/python scanner/scan_repo.py pandas-dev/pandas \
  --fresh --until-complete --data-dir /tmp/gw --months 2026-08..2026-10
```

It prints one JSON line per run and then `pandas-dev/pandas 2026-08..2026-10: <ai>/<total> AI-attributed = <share>`.
Without `--until-complete`, one run is limited to 30 pages like the nightly job.

```sh
uv venv -p /opt/homebrew/bin/python3.11 .venv
uv pip install -p .venv/bin/python requests pytest ruff
.venv/bin/python -m pytest -q

```

Files: `signatures.py` (rules), `github.py` (REST client: rate limits, 202 retries, ETags, Link pagination),
`scan_repo.py` (one repo), `universe.py`, `aggregate.py`, `run.py` (nightly), `validate.py`, `tests/`.
